S05 student guide · Timers and deadlines

Goal

An academic office has ten minutes to review a request in today’s lab. How can the office receive three reminders and still lose the task at the deadline? Build the two clocks, then use the history of three requests to explain which clock fired and which task finished.

Before class

Open your local Camunda connection in Desktop Modeler, Tasklist and Operate. Use the same classroom account for both review tasks. Download thread-s05-start.bpmn, request-intake.form, review-request-s02.form and approve-request.form. Deploy the three forms. The starter contains the gateways, the review form and the due date. You will add the timers yourself.

Step 1 · Who wins the pizza order? (0–12 min)

Customer pool, OMG, BPMN 2.0 by Example, Figure 5.2. Follow the two paths immediately after Order a pizza.

1.1 Token simulation. Follow the projector. From the event-based gateway, play pizza delivery first. On a second run, choose the clock, complete Ask for the pizza, then choose delivery. Point to the gateway each time a new wait begins.

1.2 Why the original does not run as drawn. In the executable customer model, check the message name, the field that identifies the customer and the timer’s configured duration. The original figure labels the wait as 60 minutes. Read the actual value from the Modeler properties.

1.3 Predict. The customer is waiting. What happens if the pizza arrives after 30 seconds? What task opens if two minutes pass first? When can a delivery win after that?

Think about. If two customers ordered the same pizza, which field would let the engine deliver it to the correct instance?

Step 2 · Compare a due date with a timer (12–22 min)

Watch the teacher run the pizza example. Find the completed event in Operate on each visit to the gateway. Then open the academic starter, select Review request and inspect its Due date. The script upstream calculates a date five calendar days from today. Tasklist can display that date while the review is active.

Step 3 · Build the deadline and reminder (22–45 min)

  1. Save the starter as thread-s05.bpmn. On a shared cluster, set the process ID to student-request-s05-YOURINITIALS in the process properties before deploying. Leave the supplied form IDs as they are.
  2. Attach a timer boundary event to the border of Review request. Name it SLA expired. Keep Interrupting on (solid border), choose Duration and enter the static value PT10M. SLA means service-level agreement. Here the clock starts when the review becomes active.
  3. Connect this event to a new Camunda user task named Review escalated request in the Program head lane. Select a Camunda Form and enter the form ID review-request. Set priority to 90 and leave assignment empty. Connect its normal exit to the existing Needs program head? gateway. Keep the original exit from Review request.
  4. Attach a second timer boundary event to Review request. Name it Reminder, switch Interrupting off (dashed border), choose Cycle and enter the static value R3/PT2M.
  5. Connect Reminder to a script task, Log reminder. Select FEEL expression, set its result variable to the literal name remindersSent and type the expression below. End this branch with its own none end event, Reminder logged. Save and deploy.
if remindersSent = null then 1 else remindersSent + 1

Use the expression mode for the script. Both timer values are plain ISO 8601 text. Before starting, trace each boundary event with your finger. Which path rejoins the decision? Which path ends while the office is still working?

A Approve Review request immediately, before the first reminder.

For both review forms, choose Approve and complete the task. Start A and complete it first. Then start B and C close together. Measure elapsed time separately from activation of each Review request. Work on step 5 during the wait.

Step 5 · Read the evidence (52–70 min)

In Operate, select the process root and read remindersSent under Variables. Inspect Log reminder, Review request, Review escalated request and Request closed in the instance history.

  • A. Which review completed? What value did the script leave untouched?
  • B. At the first reminder, check the count has changed and the original review is still active. After you approve it, can a second reminder fire?
  • C. Compare the instances around minutes 2, 4, 6 and 10 of this review. Between the third reminder and the deadline, where is the token? At the deadline, distinguish the state of the original task from the state of the new task. Approve the new task and find the end event.

Timers can fire slightly after their scheduled time. Use task state and the count to decide when to act. If you miss B’s window, start a fresh B and keep the first run as evidence of what actually happened.

Step 6 · Change one policy (70–80 min)

In pairs, predict what would happen to case C if the reminder were a non-interrupting duration of PT2M instead of a cycle. How many reminders would be due? Would the deadline change? Keep that two-minute duration. Next predict what would happen if its first and only reminder interrupted the review. Explain each answer by following the outgoing flows.

Finish by showing your partner one instance in which the office completed the review and another in which the timer cancelled it. Keep your model for practice.
