S02 student guide: Variables, FEEL and forms

Goal

Today you will give the process data: a start form, a computed due date, a review form and a summary. You will follow each variable from where it is created to where it is read.

Start Camunda with Iniciar Camunda, open Desktop Modeler, then go down the table in order.

How to work today

  • Steps 1 and 2 are on the projector: watch, predict and answer the questions. You do not deploy Hardware retailer.
  • Steps 3 to 6 are yours. Follow this guide beside the Modeler; the teacher follows the same sequence on screen. Keep Operate and Tasklist open.
  • Finish with discussion and save your files. There is no separate class process, assessment or result submission.

Before starting an instance: check the data. Follow the path and identify every variable a form or expression will read. Check its name, type and origin. A process can finish with an empty result (null) even when no incident appears. In the tables, tick the data you checked; result means the instance produces it. These ticks are reminders for you and disappear when you reload the page. Variable numbers stay fixed within each model throughout this guide.

Two kinds of code. A grey block with a Copy button is input data. A block marked Type it yourself is an expression to type and understand. FEEL expressions below omit the leading equals sign; enable expression mode in the Modeler so the field has the = prefix. A field key or a result-variable name, such as decision or dueDate, is a literal name, not a FEEL expression.

Step 2: try FEEL before using it

On the projector. The teacher opens a FEEL field in the Modeler and its popup editor. The test context is sample data for evaluating the expression; it does not change a running instance.

2.1 Prepare the context

Use a REST connection to the running Camunda engine. Open a FEEL expression field, then Open pop-up editor. Enter this sample context:

{"studentName": "Ana Rojas", "requestType": "postponement", "days": 7}

2.2 Predict, then evaluate

Before the teacher evaluates each expression, predict its result. You will use the same editor with your own Compute due date in step 4.

Expression What to check
"Request of " + studentName a string containing the name
days > 14 a boolean
requestType = "certificate" a boolean; one equals sign compares values
today() + duration("P5D") a date five calendar days after the engine’s current date
string(today() + duration("P5D")) the same date as a string

Then write an expression that returns "urgent" for fewer than three days and "normal" otherwise:

if days < 3 then "urgent" else "normal"

Evaluate it with days equal to 2, 3 and 10. Predict all three results before changing the context. This expression is practice; it is not yet a routing rule of the running case.

2.3 Think about

  1. How does FEEL compare two values? How does it join strings?
  2. What is the difference between 7 and "7"?
  3. Why will the date result change when you repeat the exercise another day?
  4. Does changing the test context change Ana’s running instance?

Step 3: build the intake form

The problem. A student requests a certificate, recognition of a course or postponement of an exam. A person reviews the request and chooses approve or reject. The office wants a due date and a short summary. Today every request follows the same route; the different routes come in session 3.

Open your thread-s01.bpmn and save it as thread-s02.bpmn. Keep the process id student-request and process name Student request. This is the result you are building in steps 3 and 4:

3.1 Follow the variables

These numbers stay the same in the tables of the running case:

# Variable Type Created in Read in
1 requestType string start request-intake visibility, review-request, Build summary
2 studentId string start form review-request
3 studentName string start form review-request, Build summary

5 course string start form review-request

3.2 Create the fields

In the Modeler, File → New file → Form (Camunda 8). Set the form id to request-intake. Build the fields below; a field’s Key is the name of the variable it produces when the form is submitted.

# Component Key Label Configuration
3 Text field studentName Full name required
2 Text field studentId Student ID (RUT) required
4 Text field studentEmail E-mail required; e-mail validation
1 Select requestType Type of request required; values postponement, recognition, certificate
5 Text field course Course required
6 Number days Days of postponement required when visible
7 Text area reason Reason optional

For the select, use labels Postponement of an exam, Recognition of a course taken elsewhere and Certificate of enrolment. Check the stored values, not only the labels.

Select days. In Hide if, enable expression mode and type:

requestType != "postponement"

In the form preview, select postponement: days must be visible. Select certificate or recognition: it must be hidden. This visibility rule changes the form; it is not a BPMN routing condition.

3.3 Link the form

Save as request-intake.form and deploy the form. In thread-s02.bpmn, select Request received → Form → Camunda Form (linked) → form id request-intake. Save the model; you will deploy it after step 4.

3.4 Think about

  1. Why can the file be renamed while its linked form id stays request-intake?
  2. Is the select label the value stored in requestType?
  3. Does hiding days make it unnecessary for every possible request?

Step 4: compute, review and summarise

4.1 Compute the due date

Insert a Script task Compute due date between Request received and Review request. Implementation: FEEL expression. Type:

string(today() + duration("P5D"))

Set Result variable to dueDate. Open the popup editor and evaluate the expression before deploying.

For this exercise the office allows five calendar days for every request. The requested postponement days does not determine dueDate; counting working days would need another rule.

4.2 Add the review form

Open review-request-s02.form. Its form id is review-request; its filename is different. Inspect:

  • The text component displays values such as {{studentName}}, {{requestType}} and {{dueDate}}.
  • The required radio field has key decision: label Approve stores "approved"; Reject stores "rejected".
  • The optional text area has key comment.

Deploy the form. Select the Camunda user task Review request → Form → Camunda Form (linked) → form id review-request.

4.3 Build the summary

Insert a Script task Build summary between Review request and Request closed. Implementation: FEEL expression. Type:

"Request of " + studentName + " (" + requestType + "): " + decision

Set Result variable to summary. Check that the entire route matches the figure in step 3. Both approved and rejected requests use this route today.

4.4 Check and deploy

Save and deploy thread-s02.bpmn.

4.5 Think about

  1. Which values exist before Review request is completed? Which are created afterwards?
  2. Why does Build summary come after Review request?
  3. What reads the result-variable name? What evaluates the expression?

Step 6: a wrong result without an incident

6.1 Predict the missing value

Start C-1 from the Modeler using B-1’s JSON with studentName omitted. Keep every other value and the correct model. Before starting, revisit row 3 of the data table: Build summary reads a name that this start does not provide. Predict the form display, summary and instance state.

6.2 Inspect and repair the input

Open Review request: the name is missing. Approve and complete. Inspect the instance in Operate: it can reach Request closed with summary equal to null and no incident. A completed instance is not sufficient evidence of a correct result.

Repair the input by restoring studentName and start a new instance. Approve and compare its summary. Editing a completed instance is not how you rerun Build summary.

6.3 Think about

  1. Why did the start-form requirement not protect C-1?
  2. If a form key is Decision but the expression reads decision, are they the same variable?
  3. What else must you inspect besides whether the instance completed?

Closing discussion

Explain the life of one variable: where it is created, its type, who changes it and where it is read. Compare the JSON start with the form start, and explain why a missing input can produce null without an incident. Use the questions to repeat the exercises independently; there is no final registration or submission.
