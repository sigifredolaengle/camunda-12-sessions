S04 student guide · FEEL for academic requests

Goal

An academic office receives a list of courses. Which credits count towards recognition, when is the review due, and which requests need a second reading? By the end you will calculate all three answers from one JSON request and inspect the result in a running instance.

Step 1 · What makes the token move? (0–10 min)

1.1 Token simulation. Follow the teacher through the normal-post branch of the S03 retailer variant. At the insurance gateway choose the path to Take out extra insurance. Who chose it?

1.2 Why the drawing alone cannot decide. Inspect the conditional arrow. Check the form supplies the boolean insuranceRequired and the instance supplies a numeric orderValue. Find the other outgoing flow whose condition is always true.

1.3 Predict. Read insuranceRequired = true or orderValue > 1000. With insurance unchecked, predict the condition at 999, 1000 and 1001. What changes if insurance is checked at 999?

Think about. A clerk asks whether 1000 itself qualifies. Which character in the expression settles the question?

Step 2 · Read the request (10–20 min)

2.1 Set the context. Paste the following in Context. Keep this baseline for all exercises. Each array entry represents one course. The office counts only courses with evidence.

{
  "request": {
    "id": "R-41",
    "received": "2026-11-28",
    "courses": [
      {"code":"OR", "credits":6, "evidence":true},
      {"code":"BPM", "credits":4, "evidence":false},
      {"code":"IS", "credits":5, "evidence":true}
    ]
  },
  "limit": 10
}

2.2 Predict values and types. Evaluate request.courses[1].code, request.courses[-1].credits and request.courses.evidence. Write down which returns a list. Then try request.courses[4].

Think about. Why would comparing request.received with a date require a conversion? Locate the quotes in the JSON.

Step 3 · Calculate eligible credits (20–36 min)

3.1 Select. Write a filter that keeps courses with evidence. Project the course codes from the result. Predict which two codes will appear.

request.courses[evidence = true].code

3.2 Transform and aggregate. Using the same filter, write a for c in ... return ... that produces the list of eligible credit values. Replace its projection with .credits on the filtered list and compare. Use sum to calculate the total. The office defines an empty eligible list as zero credits. Type the expression below and flip both true flags to false. Restore the baseline afterwards.

if count(request.courses[evidence = true]) = 0 then 0
else sum(request.courses[evidence = true].credits)

3.3 Check the evidence. Write one expression with some to detect missing evidence and another with every to check that all courses have evidence. Run both on the baseline and on an empty course list. Restore the baseline.

Think about. Can “every course has evidence” distinguish an empty request from a fully documented request?

Step 4 · Set a deadline and decide (36–50 min)

4.1 Add five calendar days. Convert the ISO 8601 string request.received with date(...) and add duration("P5D"). Predict the month before evaluating. Change the input to "2026-02-30", observe the result of the conversion and restore the baseline.

4.2 Compare instants. Predict the elapsed time between the two instants. Test whether the difference is zero:

(date and time("2026-11-28T09:30:00-03:00") -
 date and time("2026-11-28T12:30:00Z")) = duration("PT0S")

Replace the second time with 09:30:00Z. Explain the two results. How does duration("PT5M") differ from duration("P5M")?

4.3 State the decision. A second reading is required at or above the limit. In a fresh Playground context enter {"totalCredits":10,"limit":10}. Write if ... then "second" else "office". Predict the results for 9, 10 and 11 credits. In this context the JSON supplies totalCredits. In the process you are about to build, the engine will calculate it.

Step 5 · Run the calculation in Camunda (50–68 min)

5.1 Build. Create a Camunda 8 BPMN diagram. Set the process ID to recognition-feel-lab (append your initials on a shared cluster). Connect a start event to a script task named Assess recognition, then to an end event. Select FEEL expression as the script implementation and enter assessment as the literal Result variable. Type the expression. Within a FEEL context, later entries can use earlier entries.

{
  eligible: request.courses[evidence = true],
  totalCredits: if count(eligible) = 0 then 0 else sum(eligible.credits),
  due: string(date(request.received) + duration("P5D")),
  route: if totalCredits >= limit then "second" else "office"
}

5.2 Predict, deploy and inspect. Save as recognition-feel-lab.bpmn and deploy. Start A with the JSON from step 2. For B use the same JSON, change the ID to R-42 and set the OR course’s evidence to false. Check the inputs before each start.

# Value Type and source A B
1 request.courses list at start, read by filter
2 request.received ISO date string at start, read by deadline
3 limit number at start, read by route
4 assessment context produced by script result result

In Operate, open each instance, select the process root and expand assessment in Variables. Compare eligible, totalCredits, due and route with your predictions. Does changing evidence affect the deadline?

Think about. Where would you put assessment.route = "second" if you wanted the process to take a different path?

Step 6 · Repair the boundary and translate to DMN (68–76 min)

6.1 Break and repair. In the Playground use the step 4.3 context and change >= to >. Which of 9, 10 and 11 detects the mistake? Repair it and rerun that case.

6.2 Fill a two-row decision table on paper. Input expression assessment.totalCredits (number), output route (string), fixed limit 10 for this table. Choose Unique, so at most one rule may match each input. Write the two input tests and the two quoted outputs. Trace 9, 10 and 11. How would you keep the threshold configurable if each request had its own limit?

Close · Explain your result (76–80 min)

Show your partner the two values of assessment.route in Operate. Trace one difference back to a field in the original JSON. Which part of your explanation would still hold if the decision moved into DMN?

Further practice. (1) Flag duplicate course codes using count and distinct values. Try two copies of OR. (2) A submission is late only after the deadline. Write the comparison and try the due date and the next day. (3) An empty request should go to "incomplete". Give this rule precedence and check that cases A and B still get their original routes.
