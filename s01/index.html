S01 student guide: From drawing to running

Goal

Deploy a process, follow an instance in Operate, complete its work in Tasklist, and distinguish a process id from its name and versions.

Before class

The four installation checks in 0 setup must pass. In the lab, double-click Iniciar Camunda. Open the following in order:

Operate http://localhost:8080/operate Inspect process versions, instances and tokens. User and password: demo / demo.

How to work today

  • Step 1 is on the projector. Watch, predict and answer the questions; you do not deploy the worked example.
  • Steps 2 to 5 are yours. Keep this guide beside the Modeler, Operate and Tasklist.

Before starting an instance: check the data. Today’s running case reads no process variables: its only task waits for a person. The worked example does read data; check that table before predicting a path. The table checkboxes are reminders, not submissions; reloading clears them.

Step 1: the worked example — from a drawing to a running process

On the projector. First follow the original OMG Incident management drawing in Token Simulation; then see why it needs adaptation before the engine can run it.

1.1 Token simulation: follow every path

The teacher opens the original drawing and switches on Token Simulation. At each exclusive gateway, choose a branch and follow the token to Explain solution and the end. No deployment or process variables are needed for this simulation.

Path can handle myself? Finished? Unsure? Tasks after the first review
A yes not reached not reached Explain solution
B no yes not reached Handle 1st level issue → Explain solution
C no no no Handle 1st level issue → Handle 2nd level issue → Explain solution
D no no yes Handle 1st level issue → Handle 2nd level issue → Provide feedback → Explain solution

Only one branch is chosen at each exclusive gateway. In the simulation, the teacher chooses; next, the engine will need data to make those choices.

1.2 Why the original does not run

The teacher attempts to deploy the original. Check each item in the Modeler and read the errors before opening the adapted model.

Checked? Item to inspect Original drawing Adaptation for this class
Executable process A descriptive process, not configured to execute Mark the process executable
Gateway outgoing flows Questions and branch labels without executable conditions Conditions on the arrows and a default flow
Message start No complete executable message configuration A none start, started by hand; messages come later in the course
Task types Abstract tasks User tasks, so the engine waits for a person in Tasklist

The task-type item is a behaviour problem, not necessarily a deploy error: an abstract task can pass the token on without asking anyone to work. Compare the original with the adapted model after checking all four items.

The teacher deploys the adapted model. Before each start, predict the path from the data. These are the variables read by its conditions:

Follow the two instances in Operate and complete their human work in Tasklist. Compare what the engine does with the paths in the token simulation.

1.4 Think about

  1. What determined the branch in Token Simulation, and what determines it on the engine?
  2. Which adaptations prevent a deploy error, and which make a person’s work appear in Tasklist?
  3. Does the gateway read its question label or a variable?
  4. Who decides the value, and who follows the matching flow?
  5. Does drawing a lane assign a user to its tasks?

Step 2: model, deploy and complete one instance

The problem. A student sends a request. A person reviews it and closes it. Later sessions will add request types, data, decisions and notifications; today the model has only these three elements.

2.1 Build the model

  1. In Desktop Modeler: File → New file → BPMN diagram (Camunda 8).
  2. Select the blank canvas. Set process ID student-request and Name Student request.
  3. Draw Request received → Review request → Request closed.
  4. Change Review request to User task with the wrench menu.
  5. Save as thread-s01.bpmn.

2.2 Deploy and start

  1. Rocket icon → Camunda 8 Self-Managed, endpoint http://localhost:8080, no authentication → Deploy.
  2. Before starting, check the model: it reads no variables, so there is no JSON to enter.
  3. Play icon → Start instance without variables.
  4. In Operate, find student-request and open the instance.

Checkpoint 1. Before completing anything, where is the token? Which event will let it move?

2.3 Complete the work

  1. In Tasklist, open Review request → Assign to me → Complete task.
  2. Return to Operate and wait for the instance to show Completed.
  3. Locate the completed Review request in the instance history and explain what allowed the token to reach the end.

2.4 Think about

  1. How does deploying a model differ from starting an instance?
  2. Why can an instance remain active without consuming human work automatically?
  3. Which tool changes the drawing, which shows the token, and which lets a person complete work?

Step 3: keep another instance alive

3.1 Start and inspect

Start a second instance, again without variables. Leave Review request open. Find it in Operate and compare it with the completed instance.

3.2 Think about

  1. Do the two instances share a token?
  2. Do they use the same deployed process version?
  3. What would happen to the waiting instance if you deployed another version?

Step 4: name, id and version

4.1 Change only the name

Keep process ID student-request. Change its name to Student request (test) and deploy. Inspect the versions in Operate: the same id now has another version. Deploying the identical file again does not create a third version.

4.2 Change only the id

Change the ID to student-request-test and deploy. Find the separate process in Operate. It has its own version sequence.

Restore the ID to student-request in your saved file. Keep both versions of the running case and compare them in Operate.

4.3 Think about

  1. What identifies a process for the engine?
  2. Why does changing its name differ from changing its id?
  3. Did the active instance move to the new version?

Step 5: clean up the test process

5.1 Delete the separate test process

In Operate, filter process student-request-test and one version. Use Delete, read the confirmation and confirm. If it has multiple versions, remove each one. Wait until it disappears.

Do not delete student-request: you use it to compare versions and continue the running case in the next session.

5.2 Inspect the deletion rules

Select the version of student-request containing the waiting instance. Hover over Delete without clicking. Explain why it is disabled.

  • Deletion is per version, not per file.
  • A version with running instances cannot be deleted until they are cancelled.
  • Deleting a version also removes its finished instances, variables and history.
  • Other versions are unaffected; if the latest is deleted, an earlier remaining version becomes latest.

5.3 Think about

  1. Why can the test process be deleted while the version containing the waiting instance cannot?
  2. What evidence would disappear if you deleted a version with completed instances?
  3. How can you tell that you changed the id rather than only the name?

Closing discussion

Show a completed instance and another waiting at Review request. Explain which version each uses and what happened when the process name and id changed. Compare with the teacher’s demonstration.

There is no verification model to deploy, per-class assessment, result registration or submission. Use the questions and expected behaviour to study independently and repeat any exercise you need.
