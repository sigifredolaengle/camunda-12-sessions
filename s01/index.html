Step 1: the worked example — from a drawing to a running process

On the projector. The teacher opens the original OMG Incident management model, tries to deploy it, and then deploys the adapted version.

1.1 Why the original does not run

Look for the executable process setting, the start event, the task types and the gateway conditions. Read each deploy error with the teacher. An abstract task has no human work attached to it; a user task waits in Tasklist.

1.2 Predict, then follow two instances

The teacher starts two instances. These are the variables read by the example:

# Variable Type Read in Comes from Checked?
1 canHandle boolean condition after Handle question entered by the teacher; absent in the first instance
2 finished boolean condition after first-level support entered by the teacher if that path needs it
3 unsure boolean condition after second-level support entered by the teacher if that path needs it

In the first instance, canHandle is absent: predict which outgoing flow is taken. In the second, the teacher sets canHandle to true. Follow the tokens in Operate and the work in Tasklist.

1.3 Think about

  1. Which changes were needed before the model could be deployed?
  2. What does Can handle myself? read: its question label or a variable?
  3. Who decides the value, and who follows the matching flow?
  4. Does drawing a lane assign a user to its tasks?

Step 2: model, deploy and complete one instance

The problem. A student sends a request. A person reviews it and closes it. Later sessions will add request types, data, decisions and notifications; today the model has only these three elements.

2.1 Build the model

  1. In Desktop Modeler: File → New file → BPMN diagram (Camunda 8).
  2. Select the blank canvas. Set process ID student-request and Name Student request.
  3. Draw Request received → Review request → Request closed.
  4. Change Review request to User task with the wrench menu.
  5. Save as thread-s01.bpmn.

2.2 Deploy and start

  1. Rocket icon → Camunda 8 Self-Managed, endpoint http://localhost:8080, no authentication → Deploy.
  2. Before starting, check the model: it reads no variables, so there is no JSON to enter.
  3. Play icon → Start instance without variables.
  4. In Operate, find student-request and open the instance.

Checkpoint 1. Before completing anything, where is the token? Which event will let it move?

2.3 Complete the work

  1. In Tasklist, open Review request → Assign to me → Complete task.
  2. Return to Operate and wait for the instance to show Completed.
  3. Note its instance key: the final check must find actual execution of the user task, not just a completed process.

2.4 Think about

  1. How does deploying a model differ from starting an instance?
  2. Why can an instance remain active without consuming human work automatically?
  3. Which tool changes the drawing, which shows the token, and which lets a person complete work?

Step 3: keep another instance alive

3.1 Start and inspect

Start a second instance, again without variables. Leave Review request open. Find it in Operate and compare it with the completed instance.

3.2 Think about

  1. Do the two instances share a token?
  2. Do they use the same deployed process version?
  3. What would happen to the waiting instance if you deployed another version?

Step 4: name, id and version

4.1 Change only the name

Keep process ID student-request. Change its name to Student request (test) and deploy. Inspect the versions in Operate: the same id now has another version. Deploying the identical file again does not create a third version.

4.2 Change only the id

Change the ID to student-request-test and deploy. Find the separate process in Operate. It has its own version sequence.

Restore the ID to student-request in your saved file. Keep both versions of the running case for the check.

4.3 Think about

  1. What identifies a process for the engine?
  2. Why does changing its name differ from changing its id?
  3. Did the active instance move to the new version?

Step 5: clean up the test process

5.1 Delete the separate test process

In Operate, filter process student-request-test and one version. Use Delete, read the confirmation and confirm. If it has multiple versions, remove each one. Wait until it disappears.

Do not delete student-request: its completed history and waiting instance are evidence for this session.

5.2 Inspect the deletion rules

Select the version of student-request containing the waiting instance. Hover over Delete without clicking. Explain why it is disabled.

  • Deletion is per version, not per file.
  • A version with running instances cannot be deleted until they are cancelled.
  • Deleting a version also removes its finished instances, variables and history.
  • Other versions are unaffected; if the latest is deleted, an earlier remaining version becomes latest.

5.3 Think about

  1. Why can the test process be deleted while the version containing the waiting instance cannot?
  2. What evidence would disappear if you deleted a version with completed instances?
  3. Does the absence of a test process prove it was created earlier? Explain the limitation of a final-state check.

Step 6: final check and delivery receipt

6.1 Before checking

  • student-request has at least two deployed versions.
  • One instance completed Review request and another still waits there.
  • All versions of student-request-test have been deleted.
  • No instance of the running case has an active incident.

6.2 Run the check

In Tasklist → Processes, start S01 · End-of-session check. Enter your RUT, names and e-mail. Complete S01 · Check your work.

Version to assess: leave this optional field blank if the latest version is still the simple session-1 model. If you have already worked on later sessions, enter the session-1 version number shown in Operate. This selects the old model without replacing later versions.

The checker reads the deployed model, versions, instances and actual task histories. If it reports missing evidence, follow the named guide step, fix the work and complete the task again. The final state proves that the test process is absent; it cannot prove the earlier creation after its history has been deleted.

6.3 Confirm reception

A local pass is not a delivery receipt. S01 · Delivery receipt shows the receipt id, approval, server reception time and timing classification. Keep the receipt and complete the task.

If S01 · Delivery pending appears, restore internet or correct your RUT and choose Retry the same submission. The same attempt is not written twice. Choose Check my work again after changing the model or evidence. If the service remains unavailable, tell the teacher and keep the check instance key; delivery remains pending.

6.4 Finish independently after class

You may complete this lab independently, using this guide and the automatic feedback. The School administration determines the exam date. All laboratories close at 23:59, America/Santiago, on that day. Later submissions remain accepted and are marked Late. Until the date is configured, timing is shown as Deadline not configured; the teacher can classify existing receipts when the date is announced.

Keep your BPMN file and Camunda data. The file alone does not preserve instances or their history. On another or reset computer:

  1. Build/deploy the simple model and complete one instance.
  2. Start another and leave its user task active.
  3. Change only the name and deploy a second version.
  4. Repeat the id-change and cleanup exercise.
  5. Select a session-1 version and run the final check.

After you have a confirmed receipt, you may cancel the waiting instance if the teacher asks. If you later recheck, create another waiting instance first. Do not delete the running-case versions.

6.5 Think about

  1. What is the difference between a model, a version and an instance?
  2. A colleague says “I deployed it but nothing happens.” What do you inspect first?
  3. How do you distinguish passed work from a result received by the teacher?
