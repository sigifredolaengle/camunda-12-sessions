How to work today

  • Steps 3 to 6 are yours: work with this guide and the Modeler side by side, and keep Operate and Tasklist open in two tabs.
  • Step 7: the engine checks your work and sends the result to the teacher.

Before you start an instance: check the data. Every time you deploy and start instances, look at the model and follow the path the instance will take. For each variable: is it read on that path, and will it have a value of the right type by then, from the start of the instance, a form or a script task? Missing data gives an incident, or an empty result (null) without any warning. Where there is a table, tick the variables you checked; not required means that the path does not need it. The ticks are only for you: reloading the page clears them.

Two kinds of code in this guide.

  • A grey block with a Copy button is data: copy and paste it.
  • A block marked Type it yourself is what you are learning today. Type it in the Modeler, character by character: that is how you learn where the quotes, the equals sign and the parentheses go.

FEEL expressions are written here without the leading equals sign. In the Modeler every expression starts with it.

Step 2: the data of the process, and what goes wrong

On the projector. The data below is what the teacher uses; you do not need to run it. These are the variables of the process:

Variable Type Set or changed in Form
orderId string start of the instance shown in decide-delivery and check-insurance
weightKg number start of the instance shown in decide-delivery

The conditions read those variables: deliveryMode = "special" on the arrow “special carrier” (“normal post” is the default flow), and insuranceRequired = true on the insurance branch.

2.1 One more rule, and three instances

The teacher deploys a version of the hardware retailer with one more rule: extra insurance is also required when the order is worth more than 1000. The condition of the insurance branch becomes insuranceRequired = true or orderValue > 1000.

Before starting, the class checks the data of the three instances below (in the three, the delivery is by post). Which one does not pass?

Variable Read in Comes from B-1 B-2 B-3
orderId nobody: only shown in forms start not required not required not required
weightKg nobody: only shown in forms start not required not required not required
orderValue arrow “extra insurance required or value over 1000” start
deliveryMode arrow “special carrier” task Decide if normal post or special shipment
insuranceRequired arrow “extra insurance required or value over 1000” task Check if extra insurance is necessary

Then the teacher starts them. In the three, Decide if normal post or special shipment → post and Check if extra insurance is necessary → box not ticked.

B-1, worth 800: only Fill in a post label.

{"orderId": "B-1", "weightKg": 5, "orderValue": 800}

B-2, worth 1500: label and insurance, because of the value rule.

{"orderId": "B-2", "weightKg": 5, "orderValue": 1500}

B-3, without orderValue: it stops at the inclusive gateway with an incident.

{"orderId": "B-3", "weightKg": 5}

2.2 Repairing B-3 in Operate

B-3 stopped because orderValue > 1000 with no orderValue is neither true nor false. In Operate, tab Variables, the teacher uses Add Variable: orderValue = 900. Then tab Incidents, Retry Incident: the instance goes on from the gateway, with only Fill in a post label.

2.3 A value of the wrong type: B-5

The check also looks at the type. B-5 starts with orderValue as text. Text and a number cannot be compared: the same incident. The repair: edit orderValue (pencil icon) to the number 1500, then Retry Incident. The instance takes the insurance branch.

{"orderId": "B-5", "weightKg": 5, "orderValue": "1500"}

2.4 Rules for safe conditions

  • Compare with a single equals sign: insuranceRequired = true is false, not an error, when the variable does not exist.
  • Guard an ordering comparison, so that a missing value gives false: amount != null and amount > 100.
  • Give each variable the right type: 1500, not "1500".
  • Always give an exclusive gateway a default flow. Without it, if no condition is true, the instance stops with an incident (you will do this in step 6).

2.5 Think about

  1. Which variables come from the start of the instance, and which from a form?
  2. Why did B-2 take the insurance branch, if nobody ticked the box?
  3. Why did B-3 stop, and why did B-1 not?
  4. Why is "1500" not the same as 1500 for the engine?
  5. After Retry, does the instance start again from the beginning?

3.1 Route by type

  1. After Compute due date, add an exclusive gateway Type of request?.
  2. Draw an arrow from it to a new script task Issue certificate. Name the arrow “certificate”, select it (the arrow, not the diamond) and set its condition:
requestType = "certificate"
  1. Issue certificate is a script task (FEEL expression) with result variable certificateNumber:
"CERT-" + studentId + "-" + string(today())
  1. The arrow “needs review” goes to Review request. Mark it as default flow (wrench icon on the arrow).

3.2 Decide

  1. After Review request, add an exclusive gateway Approved?.
  2. Arrow “approved” to a script task Register decision (expression true, result variable registered). No condition reads registered: it only leaves a record of the approval. The condition of the arrow:
decision = "approved"
  1. Arrow “rejected”, marked default flow, to a script task Prepare rejection letter, result variable letter. The parentheses around the if are required: without them the model does not deploy.
"Dear " + studentName + ", your request was rejected. " + (if comment = null then "" else comment)

3.3 Merge, deploy and try

  1. Why does the arrow “needs review” deploy without a condition?

  1. After the merge, an inclusive gateway Who must be informed? with three arrows, each to a script task:
Arrow Script task Result variable
always Notify student studentMessage

  1. The conditions of the three arrows:
true
requestType = "postponement"
requestType = "recognition" and decision = "approved"
  1. The expressions of the three tasks, in the same order:
"To " + studentEmail + ": your " + requestType + " request was processed."
"Instructor of " + course + ": postponement request of " + studentName
"Registrar: recognise " + course + " for " + studentId

Step 6: break it and repair it

  1. In Approved?, select the arrow “rejected”, wrench icon, Sequence flow: it is no longer the default. Deploy. What does the Modeler say?
  2. Delete the arrow “rejected” (leave Prepare rejection letter alone). Deploy. Start instance 3 again (its data passed the check of step 5: what is missing now is an arrow) and reject it in Tasklist. In Operate, what does the instance show?
  3. Repair: put the arrow back, mark it default flow and deploy. Then, in Operate, cancel the stopped instance (Cancel instance): a new version does not move it.

Step 7: the end-of-session check

In Tasklist, tab Processes: S03 · End-of-session check → Start process (Iniciar proceso), and fill in your RUT, names and e-mail. Then complete the task S03 · Check your work.

The engine reads your latest student-request, your three instances and the incident of step 6. If something is missing, the task comes back with Feedback: fix it and complete the task again. When everything is there, your result goes to the teacher. After a deploy, wait a few seconds before you complete the task.
